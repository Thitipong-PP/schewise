# Schewise

Open-source, AI-assisted database management for software engineers.

Schewise aims to bring review, history, environment management, mock data,
schema mapping, and harmonization to database projects.

**Current milestone:** a runnable Go/Fiber API, Next.js web app,
PostgreSQL-backed authentication, scoped authorization and administration
APIs/UI, invite-only onboarding, local HTTPS, durable audit events, and
contributor CI. Target database connections, schema versioning/rollback, mock
database endpoints, harmonization, AI, and CD are not implemented yet. See the
[roadmap](docs/roadmap.md).

## Run locally

Install Docker Engine/Desktop with Compose, Node.js 26, and Make. From the root:

```sh
make init
make docker-up
```

`make init` generates unique local credentials in a Git-ignored `.env` and does
not overwrite it. Review the file before starting. The initial email is
`admin@example.test`; the generated password is `SCHEWISE_ADMIN_PASSWORD` in
`.env`. Never commit that file. Existing accounts are not reset on restart.

In another terminal, export the public local CA:

```sh
make local-ca
```

Trust the certificate generated by your own stack before opening
**[https://localhost:8443](https://localhost:8443)**. On macOS:

```sh
security add-trusted-cert -r trustRoot \
  -k "$HOME/Library/Keychains/login.keychain-db" .local/root.crt
```

This adds user-level CA trust using your login keychain, without admin-domain
trust. See the [HTTPS and authentication guide](docs/authentication.md) for
trust, removal, and other platforms. Do not bypass browser certificate warnings.
Session cookies are always Secure, HttpOnly, and SameSite=Lax. After the first
user, accounts can only be created by accepting an authorized invitation. Public
registration is closed, including for administrators.

```sh
curl --cacert .local/root.crt https://localhost:8443/api/v1/health
make auth-smoke
```

The health endpoint reports process liveness, not database readiness. The API
and web use loopback-only HTTP development ports 8080/3000 internally; browser
login uses the HTTPS gateway. PostgreSQL is published only at 127.0.0.1:5432.

Web edits in `apps/web/src` hot reload. After Go edits, use
`docker compose restart api`. Rebuild after dependency/configuration changes.
`make docker-down` stops services and preserves database and certificate
volumes.

## Access model

Units form an organization tree with one permanent root and a maximum depth of
six. Users receive roles through unit or connection assignments; an assignment
at a unit applies to its descendants. Effective permissions are the union of
matching assignments, and access is denied when none grant the requested
permission. Units default to `inherit_access=true`. A unit with inheritance
disabled includes its own assignments but stops grants from higher units,
including for descendants and owned connections. A built-in Administrator
assignment at root always bypasses this boundary; custom clones do not. The
root's flag is permanently true, and moving a unit preserves its flag. Narrower
assignments add permissions within the resulting inheritance chain.

Four immutable system roles are seeded: Administrator, Manager, Developer, and
Viewer. Custom roles and cloning are available through the Roles page and API.
System-level permissions require root assignments. Delegation requires both
membership-management permission and every permission being delegated; the last
active root Administrator is protected. Every successful metadata mutation and
its audit entry commit together.

After signing in, Organization shows readable units. Open a unit to inspect its
members and assign or revoke roles. Moving/deleting a unit requires a dry-run
impact review in the confirmation dialog. Access explorer accepts a resource, a
user, or both: browse a unit's users, inspect a user's accessible units,
optionally filter by permission, or explain a specific user/resource/permission
combination. Audit log supports actor/action/time filters. Controls follow
server-evaluated permissions and the Go API rechecks every operation. Unreadable
inherited origins are hidden individually, and assignments outside your
delegation authority are read-only. The parent-access toggle requires
`unit:manage_members` and an impact confirmation. A change that would remove the
actor's membership-management permission is rejected; root Administrators retain
their bypass. The impact includes before/after roles and permissions, affected
users, and connections.

Revocation uses `CanRevoke`: the assignment scope must lie within the actor's
own unit subtree, the actor needs `unit:manage_members` there, and must hold
every permission in the assigned role. Meeting these checks permits
self-revocation, except for the last active root Administrator. Developers
cannot revoke assignments. An ancestor grant cannot be revoked from a child; use
an inheritance boundary to stop its effect instead. Hidden inherited sources and
blocking units never expose their names/IDs in members or Explain.

To bootstrap the first administrator, set `SCHEWISE_ADMIN_EMAIL` and
`SCHEWISE_ADMIN_PASSWORD` before the first API startup (`make init` generates
local values). This creates the initial root Administrator only; changing these
variables never resets an existing account.

To add a custom role:

1. Sign in with root `role:manage` and the permissions you intend to grant.
2. Open **Roles → Create role**, name it, and tick the grouped permissions.
   Alternatively, clone a system/custom role, then edit the copy.
3. Open the target unit and choose **Assign role** for an existing user, with an
   optional note. You need `unit:manage_members` and every delegated permission
   at that scope. Roles containing system permissions can only be assigned at
   root.

System roles are read-only. A custom role cannot be deleted while assigned. New
accounts use the Invites page; there is no public sign-up UI.

## Invite teammates

1. Bootstrap the first root Administrator with `SCHEWISE_ADMIN_EMAIL` and
   `SCHEWISE_ADMIN_PASSWORD` on first startup. Existing accounts are preserved.
2. Sign in and open **Invites → Create invite**. Root `user:manage` is required
   for every invite operation; the issuer must also pass `CanAssign` for the
   selected role and unit. Enter the teammate's email, scope, role, and optional
   note. Existing users should receive assignments directly instead.
3. Copy the link from the one-time dialog and share it privately. The link
   cannot be retrieved later. Regenerate revokes it and creates a new link;
   revoke disables it. Only one pending, unexpired invite per normalized email
   is allowed. The list includes pending, used, expired, and revoked records.
4. The invited person opens `/invite/<token>`, sees the fixed email, role and
   unit, and supplies a display name and password. Acceptance creates the user,
   assignment, authenticated session and audit entries in one transaction.

Set `PUBLIC_BASE_URL` to the browser-facing HTTPS origin (for example
`https://localhost:8443`), matching `SCHEWISE_ORIGIN`. It defaults to that
origin when omitted. Links never use an incoming Host header. Set
`SCHEWISE_INVITE_TTL=168h` for the default seven-day expiry; supported lifetimes
are `1m` through `720h`. Container environments pass both settings to Go.

Passwords must contain 12–128 Unicode characters, at most 512 UTF-8 bytes, and
must not match the small built-in common-password denylist. There are no
composition rules. Login keeps compatibility with previously stored hashes.

`POST /api/v1/auth/register` is bootstrap-only on an empty installation, guarded
by Origin and synchronizer CSRF. It creates the first root Administrator and
closes immediately under the same lock as env bootstrap. Normal process startup
already performs env bootstrap before listening; there is no public sign-up page
or registration-enabling flag.

Invite tokens contain 32 random bytes and only SHA-256 digests are stored.
Unavailable tokens return one generic error. Role/scope and issuer authority are
rechecked at acceptance; invalidated invites stay unused. Public token endpoints
share per-IP and global per-process rate limits. No SMTP transport is installed:
the optional `auth.Mailer` defaults to a no-op. Account settings, password
reset, and 2FA remain deferred. See [authentication](docs/authentication.md) for
limits.

The API contract is generated from backend DTOs/routes in
[OpenAPI](docs/openapi.json), with generated TypeScript types checked in CI.
Connection scopes have a fail-closed ownership adapter, not a real connection
catalog or connector yet. See the [authorization guide](docs/authorization.md).

## Develop without API/web containers

Also install Go 1.27.3 and pnpm 12.16.1:

```sh
npm install --global pnpm@12.16.1
make setup
make init
docker compose up -d --wait db
```

Run `make dev-api` and `make dev-web` in separate terminals. These Make wrappers
parse `.env` without shell evaluation; the Go programs themselves read only
process environment variables. Direct HTTP is useful for health/debugging, while
browser auth needs HTTPS. See the [development guide](docs/development.md) for
native HTTPS setup and commands.

## Checks

```sh
make check             # API contract, format, vet, Go/web tests, lint, TypeScript
make integration-test  # Auth/SQL tests in isolated Postgres schemas
make build             # API and migration binaries, production Next.js build
make smoke             # Production page/proxy/auth integration; ports 8080/3000 free
make auth-smoke        # Running HTTPS stack: cookies, CSRF, login, page, logout
```

Source checks can run without Postgres; database integration tests require it.
The production smoke check needs the application database, valid installation
credentials, and a web build with the default API destination. It writes only
session/audit activity. Stop running API/web containers and native dev servers
before it. Use `make help` for all commands.

CI checks real PostgreSQL integration, builds, audits, production smoke, and
Docker HTTPS startup/auth/shutdown. Actions are pinned and permissions
read-only. No CD or release publishing is configured.

## Repository layout

```text
cmd/api/                 API process lifecycle
cmd/migrate/             Application migration CLI
internal/auth/           Passwords, sessions, account bootstrap, auth audits
internal/rbac/           Scoped permission engine, metadata repositories, impact previews
internal/config/         Process environment configuration
internal/database/       PostgreSQL access and embedded Goose migrations
internal/httpapi/        Fiber routes and HTTP/integration tests
internal/apicontract/    Backend DTOs and route manifest for OpenAPI generation
cmd/apigen/              OpenAPI generator
apps/web/                Next.js App Router and authentication UI/proxy
deploy/                  Local Caddy and Postgres initialization configuration
scripts/                 Local setup and smoke checks
docs/                    Architecture, authentication, development, ADRs, roadmap
.github/                 CI, updates, issue/PR templates
```

The application database is separate from future user-connected target
databases. Read the [architecture](docs/architecture.md) and
[authentication contract](docs/authentication.md) before extending the backend.
