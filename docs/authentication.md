# Authentication and application storage

Schewise uses a dedicated PostgreSQL application database for users, roles,
sessions, and audit events. It is separate from future user-connected target
databases. Goose applies embedded migrations at API startup with a Postgres
advisory session lock.

## First installation and HTTPS

```sh
make init
make docker-up
# In another terminal, after services start:
make local-ca
```

`make init` creates a mode-0600, Git-ignored `.env` with unique random
passwords. It never overwrites an existing file or prints passwords. Review that
file before startup. The default email is `admin@example.test`; its generated
password is `SCHEWISE_ADMIN_PASSWORD`. `.env.example` contains placeholders
only.

The initial Administrator is created only when the users table is empty, inside
an advisory-locked transaction. Restarts do not reset passwords, create another
administrator, or change roles when installation variables change.

Open **https://localhost:8443**. Caddy uses a private local CA and proxies API
traffic to Fiber and page traffic to Next.js. All published ports bind to host
loopback. Use HTTPS for browser login; session cookies remain Secure everywhere.

Browsers must trust the CA generated by your own stack. On macOS, review the
exported `.local/root.crt`, then explicitly add it to your login keychain:

```sh
security add-trusted-cert -r trustRoot \
  -k "$HOME/Library/Keychains/login.keychain-db" .local/root.crt
```

This adds user-level CA trust without adding admin-domain trust. Do not bypass
browser certificate warnings. Other platforms should import the CA with their
certificate manager. Remove it from the trust store when no longer needed.
Recreating the Caddy data volume creates a different CA and requires a new trust
decision. CA private keys remain inside the Caddy volume; only the public root
certificate is exported.

CLI checks can trust it for a single process without changing OS trust:

```sh
curl --cacert .local/root.crt https://localhost:8443/api/v1/health
make auth-smoke
```

The HTTPS smoke check uses installation credentials from `.env` and a
process-scoped `NODE_EXTRA_CA_CERTS`. It creates/revokes test sessions and
writes audit events; do not point it at a production instance.

## API contract

Paths below are relative to `/api/v1`. Responses are JSON.

| Method     | Path                     | Access and behavior                                                     |
| ---------- | ------------------------ | ----------------------------------------------------------------------- |
| GET / HEAD | `/health`                | Public process liveness, not database readiness                         |
| GET        | `/auth/csrf`             | Returns CSRF token; creates a short-lived anonymous session when needed |
| POST       | `/auth/login`            | Valid CSRF, exact Origin, email/password; rotates the session           |
| POST       | `/auth/register`         | Administrator plus CSRF; creates an Administrator account               |
| POST       | `/auth/logout`           | Valid session plus CSRF; revokes session and expires cookie             |
| GET        | `/auth/me`               | Authenticated identity: UUID, email, and current role                   |
| DELETE     | `/users/{uuid}/sessions` | Administrator plus CSRF; revokes all sessions for that user             |

Login and registration accept only `email` and `password`; unknown fields are
rejected. Emails are trimmed/lowercased. Passwords require at least 12 Unicode
characters and at most 256 UTF-8 bytes. Argon2id PHC hashes use 64 MiB memory, 3
iterations, 2 lanes, a random 16-byte salt, and a 32-byte output. Unknown emails
perform dummy password verification, and failed login responses are generic.

The only seeded role is **Administrator**, granting all current capabilities.
Public registration is disabled; only an existing Administrator can create
accounts, and all accounts in this milestone are Administrators. Custom
roles/permissions, invitations, MFA, verification, and recovery are deferred.

Revocation affects subsequent requests immediately. It does not disable the
account or prevent another login with valid credentials. Already in-flight
requests may complete. Permissions are read from the database, not browser
claims.

## Session and CSRF guarantees

- The opaque authentication token has 256 bits of cryptographic randomness. The
  database stores only its SHA-256 digest, never its plaintext value.
- The cookie is `__Host-schewise_session`, with `HttpOnly`, `Secure`,
  `SameSite=Lax`, `Path=/`, and no Domain. No token is stored in localStorage.
- Anonymous CSRF sessions last 15 minutes. Authenticated sessions have an
  absolute 24-hour lifetime by default, configurable from 1 minute to 30 days.
- A separate synchronizer CSRF token lives in the database session and is
  returned by a no-store endpoint. Mutations require it in `X-CSRF-Token` and an
  exact configured `Origin`. Login is protected too; SameSite is an additional
  defense.
- Login consumes the old session and creates fresh auth/CSRF tokens atomically.
  Logout and per-user revocation delete database rows. Expired sessions are
  rejected immediately and removed by a five-minute cleanup task.
- There is no permissive CORS policy. API clients must use the same cookie/CSRF
  handshake and send the configured Origin on mutations.

Next.js 16 uses `src/proxy.ts` (formerly middleware.ts) for redirects. It
validates sessions with Go, rather than trusting cookie presence. The protected
page also checks identity server-side. Go authorizes every protected API.
Authentication outages return 503 and never grant access.

## Logs and durable audit

Zap emits JSON for every API request: request ID, matched route, method, status,
duration, actor UUID when known, and socket peer IP. Unmatched paths are
redacted. Request bodies, query strings, headers, cookies, passwords/hashes,
CSRF tokens, session tokens, and raw database error details are never serialized
into logs. System lifecycle, migrations, cleanup, and operation failures use Zap
too.

`audit_events` persists bootstrap, successful/failed login, account creation,
logout, access/permission denial, CSRF rejection, rate-limit denial, and session
revocation. Successful auth/account mutations commit with their audit event in
one transaction. Audit failure rolls back the associated mutation. The request
failure remains visible in operational logs.

Audit events have no automatic deletion policy yet. This is application-level
audit storage, not tamper-proof storage against a database owner or host admin.
Forward stdout to a persistent collector for long-term operational logs. UI
clicks/keystrokes/static assets are not analytics events; HTTP logging here
means API requests. Next.js development output remains framework logging.

## Operational boundaries

Login and CSRF bootstrap are rate-limited per instance, and password work is
limited to four concurrent operations. The limiter uses the socket peer and
ignores untrusted forwarding headers. Clients behind the development gateway
share that peer limit. Broader deployment needs an explicitly trusted proxy
configuration and shared throttling across replicas.

The API's `schewise` database role is not a superuser and cannot create
databases or roles; it owns this application's database and applies its
migrations. Only the initialization account has cluster administration rights. A
production deployment can further separate migration and runtime database roles.

Protect `.env`, back up the Postgres volume, and protect the Caddy private CA
volume. Production deployment, certificate issuance, secret management, backups,
MFA/recovery, audit retention, and monitoring require a separate deployment
plan.
