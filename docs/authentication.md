# Authentication and application storage

Schewise uses a dedicated PostgreSQL application database for users, roles,
sessions, and audit events. It is separate from user-connected target databases.
Goose applies embedded migrations at API startup with a Postgres advisory
session lock.

## First installation and HTTPS

```sh
make init
make docker-up
# In another terminal, after services start:
make local-ca
```

`make init` creates a mode-0600, Git-ignored `.env` with unique random
passwords. It never overwrites an existing file or prints passwords. Review that
file before startup. The default email is `admin@example.test`; its generated
password is `SCHEWISE_ADMIN_PASSWORD`. `.env.example` contains placeholders
only.

The initial Administrator is created only when the users table is empty, inside
an advisory-locked transaction. Restarts do not reset passwords, create another
administrator, or change roles when installation variables change.

Open **https://localhost:8443**. Caddy uses a private local CA and proxies API
traffic to Fiber and page traffic to Next.js. All published ports bind to host
loopback. Use HTTPS for browser login; session cookies remain Secure everywhere.

Browsers must trust the CA generated by your own stack. On macOS, review the
exported `.local/root.crt`, then explicitly add it to your login keychain:

```sh
security add-trusted-cert -r trustRoot \
  -k "$HOME/Library/Keychains/login.keychain-db" .local/root.crt
```

This adds user-level CA trust without adding admin-domain trust. Do not bypass
browser certificate warnings. Other platforms should import the CA with their
certificate manager. Remove it from the trust store when no longer needed.
Recreating the Caddy data volume creates a different CA and requires a new trust
decision. CA private keys remain inside the Caddy volume; only the public root
certificate is exported.

CLI checks can trust it for a single process without changing OS trust:

```sh
curl --cacert .local/root.crt https://localhost:8443/api/v1/health
make auth-smoke
```

The HTTPS smoke check uses installation credentials from `.env` and a
process-scoped `NODE_EXTRA_CA_CERTS`. It creates/revokes test sessions and
writes audit events; do not point it at a production instance.

## API contract

Paths below are relative to `/api/v1`. Responses are JSON.

| Method     | Path                     | Access and behavior                                                     |
| ---------- | ------------------------ | ----------------------------------------------------------------------- |
| GET / HEAD | `/health`                | Public process liveness, not database readiness                         |
| GET        | `/auth/csrf`             | Returns CSRF token; creates a short-lived anonymous session when needed |
| POST       | `/auth/login`            | Valid CSRF, exact Origin, email/password; rotates the session           |
| POST       | `/auth/register`         | Empty installation only, plus CSRF; closes after first user             |
| POST       | `/auth/logout`           | Valid session plus CSRF; revokes session and expires cookie             |
| GET        | `/auth/me`               | Authenticated identity: UUID, email, display name, and role             |
| DELETE     | `/users/{uuid}/sessions` | Root user:manage plus CSRF; revokes all sessions for that user          |

Login and registration accept only `email` and `password`; unknown fields are
rejected. Emails are trimmed/lowercased. New passwords require 12–128 Unicode
characters (at most 512 UTF-8 bytes) and reject a small common-password list.
Argon2id PHC hashes use 64 MiB memory, 3 iterations, 2 lanes, a random 16-byte
salt, and a 32-byte output. Unknown emails perform dummy password verification,
and failed login responses are generic.

The four seeded system roles are **Administrator**, **Manager**, **Developer**,
and **Viewer**. Role names are display metadata, never authorization checks.
Permissions come from scoped assignments through the RBAC engine; see
[authorization](authorization.md).

Public registration closes after the first account. Subsequent accounts require
invitations with root `user:manage` and `CanAssign` for the intended role/scope.
Per-user session revocation requires root `user:manage`. Role/unit/assignment
management, invitations, account settings, and admin-issued reset have HTTP APIs
and UI; email changes, MFA, verification, and personal access tokens remain
deferred.

The existing identity response's `role` string is a display-only, sorted list of
assigned role names for compatibility with the development page. It does not
represent effective permissions at a particular resource. Deactivated users
cannot authenticate, and deactivation removes their sessions in the same
transaction. A concurrent login cannot recreate a session after deactivation.

Revocation affects subsequent requests immediately. It does not disable the
account or prevent another login with valid credentials. Already in-flight
requests may complete. Permissions are read from the database, not browser
claims.

## Session and CSRF guarantees

- The opaque authentication token has 256 bits of cryptographic randomness. The
  database stores only its SHA-256 digest, never its plaintext value.
- The cookie is `__Host-schewise_session`, with `HttpOnly`, `Secure`,
  `SameSite=Lax`, `Path=/`, and no Domain. No token is stored in localStorage.
- Anonymous CSRF sessions last 15 minutes. Authenticated sessions have an
  absolute 24-hour lifetime by default, configurable from 1 minute to 30 days.
- A separate synchronizer CSRF token lives in the database session and is
  returned by a no-store endpoint. Mutations require it in `X-CSRF-Token` and an
  exact configured `Origin`. Login is protected too; SameSite is an additional
  defense.
- Login consumes the old session and creates fresh auth/CSRF tokens atomically.
  Logout and per-user revocation delete database rows. Expired sessions are
  rejected immediately and removed by a five-minute cleanup task.
- There is no permissive CORS policy. API clients must use the same cookie/CSRF
  handshake and send the configured Origin on mutations.

Next.js 16 uses `src/proxy.ts` (formerly middleware.ts) for redirects. It
validates sessions with Go, rather than trusting cookie presence. The protected
page also checks identity server-side. Go authorizes every protected API.
Authentication outages return 503 and never grant access.

## Logs and durable audit

Zap emits JSON for every API request: request ID, matched route, method, status,
duration, actor UUID when known, and socket peer IP. Unmatched paths are
redacted. Request bodies, query strings, headers, cookies, passwords/hashes,
CSRF tokens, session tokens, and raw database error details are never serialized
into logs. System lifecycle, migrations, cleanup, and operation failures use Zap
too.

`audit_log` persists bootstrap, successful/failed login, account creation,
logout, access/permission denial, CSRF rejection, rate-limit denial, session
revocation, and RBAC metadata mutations. Authentication request IDs, outcomes,
and peer IPs live in `details`. Existing `audit_events` rows are migrated with
IDs and timestamps preserved. Successful mutations commit with their audit
record in one transaction. Audit failure rolls back the associated mutation;
operational failures remain visible in redacted Zap logs.

Audit events have no automatic deletion policy yet. This is application-level
audit storage, not tamper-proof storage against a database owner or host admin.
Forward stdout to a persistent collector for long-term operational logs. UI
clicks/keystrokes/static assets are not analytics events; HTTP logging here
means API requests. Next.js development output remains framework logging.

## Operational boundaries

Login and CSRF bootstrap are rate-limited per instance, and password work is
limited to four concurrent operations. The limiter uses the socket peer and
ignores untrusted forwarding headers. Clients behind the development gateway
share that peer limit. Broader deployment needs an explicitly trusted proxy
configuration and shared throttling across replicas.

The API's `schewise` database role is not a superuser and cannot create
databases or roles; it owns this application's database and applies its
migrations. Only the initialization account has cluster administration rights. A
production deployment can further separate migration and runtime database roles.

Protect `.env`, back up the Postgres volume, and protect the Caddy private CA
volume. Production deployment, certificate issuance, secret management, backups,
MFA/recovery, audit retention, and monitoring require a separate deployment
plan.

## Step 3: private invitations

After the first account, `/api/v1/auth/register` returns a generic 403 for all
callers; administrators create invitations instead. Env bootstrap stays the
normal installation path, before the API starts listening. No public sign-up,
registration-enable flag or public sign-up is implemented. Step 4 adds account
settings and admin-issued reset; email sending and 2FA remain deferred.

`PUBLIC_BASE_URL` is an HTTPS origin without a path/query/credentials and must
match `SCHEWISE_ORIGIN`. It defaults to the latter. `SCHEWISE_INVITE_TTL`
defaults to `168h` and accepts `1m`–`720h`. The optional `auth.Mailer` has a
no-op default. A one-time create/regenerate response is the only way to retrieve
a link; tokens and links are never stored in audit records or application logs.
Next.js incoming URL logging is disabled, and invite responses/pages use
no-store, no-referrer, and noindex. Keep any additional reverse-proxy/access
logging configured to redact invite paths; a bearer URL also remains in the
recipient's browser history until they remove it. Do not add analytics to invite
pages.

Admin APIs require live root `Can(user:manage)`, and creation/regeneration also
require `CanAssign` for the attached role/scope. Current metadata supports unit
scopes; connection invitation scopes fail closed until a connection ownership
adapter is installed. Root scopes serialize with a nullable `scope_id`; the API
uses the existing explicit root unit UUID. Lists use keyset pagination (default
50, maximum 200). Only unused and unrevoked invitations can be revoked or
regenerated; an expired one may be replaced by either regeneration or a new
invite. Regeneration revokes the old record and creates a fresh one atomically.

Acceptance requires the existing Origin/CSRF flow. The public GET exposes only
email, role name, scope name, and expiry for a usable invitation. Unknown,
malformed, expired, used, revoked, deleted-target, or no-longer-delegable links
return the same `invitation_unavailable` response. Public GET/accept routes
share 20 attempts per IP per minute and 200 attempts globally per minute per API
process, including invalid requests. Limiters use the direct peer IP; do not
trust forwarded IP headers from arbitrary clients. Multiple replicas would
require a shared limiter and reviewed trusted-proxy configuration.

Creation/acceptance and metadata mutations share the RBAC advisory lock. The
issuer must still be active, hold root `user:manage`, and pass `CanAssign` for
the current role at acceptance. This prevents role edits or revoked issuer
privileges from escalating an old invitation. Failed revalidation leaves the
invite unused. User, display name, role assignment (created by the issuer), used
state, rotated session and audits commit together, or none do. Replaying a used
link fails. Email is taken exclusively from the invite, never the form.

New password hashes use the existing Argon2id work factors with 12–128 Unicode
characters (maximum 512 UTF-8 bytes), a small case-insensitive common-password
denylist, and no composition rules. Existing hashes remain verifiable, including
older accepted passwords; the stricter policy applies to new credentials.

## Step 4: accounts, sessions, and password reset

All routes below use `/api/v1`. Authenticated mutations require the existing
exact Origin and current synchronizer CSRF token. Unknown body fields are
rejected, including email, role, or user IDs in self-service requests.

| Route                                   | Behavior                                                                                                                      |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `GET/PATCH /me/profile`                 | Read your profile/update only your display name.                                                                              |
| `POST /me/password`                     | Verify `current_password`, accept `password`, revoke other sessions and pending reset links.                                  |
| `GET /me/sessions`                      | Active sessions owned by the live account, current marker, coarse device, optional IP, timestamps; no token/hash/CSRF values. |
| `DELETE /me/sessions/{id}`              | Revoke only an owned non-secret session UUID. Missing/unowned UUIDs both return 404.                                          |
| `POST /me/sessions/revoke-others`       | Preserve current session; revoke other owned sessions.                                                                        |
| `GET /me/access`                        | Read-only effective access and per-assignment redacted sources; empty for accounts without readable units.                    |
| `GET /admin/users`                      | Root `user:manage`: email/name search, active/inactive accounts, last recorded login and role summary; keyset pagination.     |
| `POST /admin/users/{id}/deactivate`     | Root `user:manage`: use the existing last-admin guard, revoke sessions and pending resets, never delete.                      |
| `POST /admin/users/{id}/reactivate`     | Root `user:manage`: preserve password/assignments; restore no sessions/reset links.                                           |
| `POST /admin/users/{id}/password-reset` | Root `user:manage`: create a link once; revoke older pending reset links. Active targets only.                                |
| `GET/POST /reset-password/{token}`      | Public inspection/replacement, generic unavailable errors, no automatic login. POST still requires Origin/CSRF.               |

New session UUIDs are unrelated to bearer tokens. Migration 00005 preserves all
existing session tokens and initializes their last-seen timestamps from creation
time. New sessions record truncated user agents (256 Unicode characters), exact
supplied peer IPs, and a current activity timestamp. The list returns only
coarse browser/platform categories, never the raw agent. Activity updates use a
conditional database write no more than once per five minutes. Successful login
and invitation acceptance update `last_login_at`; old/null values mean unknown
history. Failed login and password reset do not update it.

`SCHEWISE_STORE_SESSION_IP=false` omits IPs for new sessions and new HTTP/auth
audit logs and hides historical IPs from session responses. Existing records and
historical logs are not erased. No trusted-forwarded-IP behavior is added: keep
network/proxy configuration consistent with the Step 3 limiter limits.
`SCHEWISE_PASSWORD_RESET_TTL` accepts `1m`–`168h`, default `24h`. Reset URLs use
`PUBLIC_BASE_URL`, with the same HTTPS-origin validation as invitation links.

Only SHA-256 digests of 32-byte random reset tokens are stored. New links revoke
older pending links transactionally. Acceptance rechecks token state, target
activity and the issuer's current root `user:manage` permission. Invalid,
expired, used, revoked, wrong-purpose, inactive-target or unauthorized-issuer
links share `reset_unavailable`. Public invite/reset attempts share the existing
20/IP/minute and 200/global/minute per-process budgets. Password changes have
5/IP/minute and 5/account/minute budgets. A wrong current password returns 400,
preserving the valid session, and records a failure audit.

Password change, password reset and deactivation serialize with login under the
shared advisory lock. Login must still see the password hash it verified before
creating a session, preventing concurrent old-password sign-ins from undoing
revocation. User metadata, credential hashes, session revocations, reset
consumption/revocation, and audit entries commit atomically or roll back. The
current session stays valid only for self-service password change. Reset revokes
all sessions and creates none. Self-deactivation is permitted while another
active root Administrator remains; the API and existing DB triggers protect the
last one. Pending reset links do not revive after reactivation.

Use the Users page's copy-once dialog to deliver reset links privately; no SMTP,
public email reset request, email change, 2FA, or personal access token support
is installed. Keep any additional proxy/access logging configured to redact both
`/invite/` and `/reset-password/` paths.

Reset links are bearer capabilities: anyone holding a valid link can choose a
replacement password, including its issuer. The admin API provides no direct
password-edit/read operation, but this manual-delivery milestone cannot verify
the recipient independently. Treat root `user:manage` as trusted
account-recovery authority for all accounts, including root Administrators.
